# 玩家体感 TAG 干员名单判定 · 共享作业说明（读我）

> 目的：为 `docs/player-tags-specify.md` 中开发者拟定的**玩家体感 TAG**（现为 11 个分文件），逐一产出"该 TAG 下的完整干员名单 + 条件 + 备注"。
> 每个执行者（agent）负责一个 TAG；产出为 JSON 批文件（`agent_workspace/_out/<批名>.json`，键＝干员名，值＝`{condition, remark, why}`），**不直接改分文件**——由主进程经 `.claude/skills/tag-batch-rewrite/scripts/_apply_batch.py` 统一回填到本目录的 `NN-*.json`（tag-part/1），合并为 `docs/player-tags-members.md`。

## 0. 项目背景（必读）

- 本项目为明日方舟干员筛选系统生产数据。已有两类 TAG：
  - **官方定义类 TAG**：`docs/official-tags-members.md`（TAG 数与关系数以该文档 §3 为准），机读字典在 `agent_workspace/tag_pipeline/`（`catalog.json`＝脚本唯一读取的字典；`merged.json`／`final_lists.tsv` 由 `official_tags/_merge_official_to_docs.py --sync-dicts` 同步；`deterministic.json` 为基础属性快照；维护层 `official_tags/`）。
  - **玩家体感类 TAG**：`docs/player-tags-specify.md`（开发者拟定的正式玩家 TAG，即本次任务的定义来源），名单结果见 `docs/player-tags-members.md`；线索来源＝PRTS 原文复核。
- 玩家 TAG 共 11 个（分文件 `NN-*.json`，tag-part/1 JSON）：决战歼灭、次数对策、吃拐一轮秒、远程消耗、插拔容错、初动增加、充电、拐杖、保人、**高档控制（原「大力推拉」「阻挡数5」已降为其子 TAG，另含「长效控制」「远距控制」）**、阵容组合。

## 1. 数据源（判定以 PRTS 原文为准）

| 源 | 用途 |
|---|---|
| `material_datas/PRTS/<干员>/<干员>.md` | **主证据源**。含 特性/天赋/技能/模组/属性/获得方式(上线时间)/召唤物信息。技能表按等级列出（Rank Ⅲ=专精3，7=7级）。 |
| `material_datas/PRTS/<干员>/*.md` | 同目录的召唤物文件（如 温蒂/工程蓄水炮.md）。**召唤物效果计入持有干员。** |
| `agent_workspace/tag_pipeline/deterministic.json` | 解析好的基础属性（再部署/阻挡/费用）与召唤物数据（block/slots/etype）。 |
| `agent_workspace/tag_pipeline/final_lists.tsv` / `merged.json` | 官方 TAG → 成员名单（按实装倒序），用于交叉锚定。 |
| `docs/official-tags-members.md` | 官方 TAG 定义与完整名单（含备注评定标准）。 |
| `docs/mechanism-understanding.md`、`docs/verification-complaints.md` | 机制判别评定标准与历史踩坑记录（避免重蹈覆辙）。 |

## 2. 判定铁律（项目既有约定，务必遵守）

1. **一切判定以 PRTS 原文（文件:行号）为证据**，不凭模型记忆；拿不准的标 `[待考]` 并写入"待开发者确认"。
2. **施加方向是第一属性**：区分"对友方/自身/敌人/召唤物"。本批 TAG 全部是**对友方/对团队**的体感能力（除个别如推拉是对敌），不要把"自身获得"误判成"能为友方提供"。
3. **召唤物/装置效果计入干员**（如酒神3技能生成的迷狂牢笼计入酒神）；**模式限定模组（ISW-α / RA-α 等集成战略/生息演算限定）同样计入**——但必须把模式限定写进「条件」（如"需开启 ISW-α 模组"），并在备注中注明该效果仅在该模式可用；多条**通用模组**之间平权、取成绩更高者；持特限证章者：通用线与特限线**分别计算**、UI 分别展示且**特限线优先展示**（见 `docs/ui-render-rules.md`）、无特限证章者默认各模组的增伤条件均满足、取更高者并把条件写进条件（`docs/rulings.md`）。
4. **区分同名不同物**：屏障(吸收值)/护盾(按层挡一次)/闪避/抵挡、脆弱(受伤↑)/攻击力加成、灼烧DoT/灼燃损伤、晕眩/停顿/束缚/战栗/麻痹……分类参照 `docs/official-tags-members.md` §2 与 `mechanism-understanding.md`。
5. **不凭当期强度**：只收机制层面成立、跨版本稳定的能力；"新神/退环境/超大杯"类强度结论不收。
6. 干员用**正式名**（与 PRTS 文件夹名一致，如"史尔特尔"不写"42"、"假日威龙陈"不写"水陈"）；异格/同名分别列（如 阿米娅(医疗)）。

## 3. 条件 / 备注 的写法（来自 `docs/concept.md` 与 specify 文档）

- **条件**：硬性达成条件。例：`精英2`、`精英2；3技能专精3`、`精英2；Y模组1级`、`精英1`；以及目标限制（`仅对重装生效`、`仅限高台`、`仅限攻回/受回干员`、`需在场上`）。若干员精零1级即具备该能力 → 写 `无`。`；` 只切在**并列要求**之间：「或」的两支合并成一条、支内用 `／`（写 `精英1＋2技能 ／ 精英2＋3技能（专三数值）；潜能3`）；面板档位、计数方式等演算前提不写进条件，写进备注的 `说明` 块。
- **备注**：信息加工后的内容——**具体数值、持续时间、隐藏机制、特殊用法、战术帮助**。不写游戏内一目了然的话；没东西可写就写 `—`。数值取 PRTS 原文，标注关键等级评定标准（专三/7级/Rank Ⅲ）；只写对筛选/使用有用的，不必抄全文；**只写与本 TAG 评定对象相关的**——与该 TAG 无关的能力整块不写、无关的演算与「未计入：X」条目也不写（见 `docs/concept.md`「备注分块」的「只写与本 TAG 相关的信息」）。
- **备注分块**（完整规范见 `docs/concept.md`「备注分块」）：单元格内单行书写，`｜` 分块、`；` 分条，两层都用 `标签：正文`。块序固定 **成绩 → 各能力块 → 说明**；能力块标签写全称（`2技能「重力自定义」`，禁 `S2`／裸 `2技能`），能力块内的条标签用维度词（`持续`／`范围`／`伤害`／`打数`／`其它`，取代旧的 `★持续` 类标记）。成绩一个情形一块（`成绩 最低可满足档（精英1 满级＋满信赖＋潜能4）`），演算式与推导**不进备注**，写进 `agent_workspace/tag_pipeline/calc_process/<干员>.json`（规范见 `docs/calc-process-spec.md`）；口径与勘误进 `说明` 块。不得出现 `★` 分类标记、`备注：`／`PRTS 备注：` 前缀、`（下详）` 类悬空引用；`文件:行号` 证据一律写进「依据」列。
- **数值纪律**（完整规范同上）：面板一律由 `tools/prts_stats.py` 复算、组成式写进 `calc_process` 的 steps 首条；模组／潜能取对本 TAG 有帮助的最高档并写进条件（模组按**绝对贡献**判、多条通用模组之间平权取成绩更高者、持特限证章者通用线与特限线分别计算并特限优先展示（`docs/ui-render-rules.md`），不得因更高档拉低比值／稀释均值而改取低档）；演算默认敌人为**纯木桩**（0 防御／0 法抗／0 闪避免伤／无减伤）——作用于敌方防/抗数值的减益与穿透不计入，承伤倍率型增伤（脆弱、通缉）照计；条件性增伤（自身状态／目标状态／布阵与数量）一律折入并把前提写进条件；成绩只允许「精英0/1 可满足的最低档＋最高档」与「特殊机制多情形」两种并列，其余取满配档；**能力块自足**（写清该能力本身：触发条件＋对象＋效果，数值影响另条）；未计入项不再逐条写进 `说明`（只写与本 TAG 判据同源的边界项）；**内部代号（范围代号、`S1/S2/S3`、`表 2A`、`路径⑤`）不入产物，但模组代号应当进产物**——统一写「中文线名（代号）」：`X模组3级（HOK-X）`、`Δ模组3级（CCR-Δ）`、`集成战略特限模组3级（ISW-α）`；成绩块**单情形一律裸 `成绩`**、多情形才带情形名与口径（面板组成式写 `calc_process` 的 steps）。
- **一名干员的多项能力只要各自符合本 TAG 的评定标准都要写**：条件写全各能力的硬性前提，备注逐项写清；不因与其它能力重叠、幅度较小或已有更强项而省略。（**符合判据者一项不漏**；不符合判据者的展开不写——两者不矛盾。）
- **模组档位**：判定能力受模组增强者，「条件」写明模组名与等级、「备注」取该档位数值；同干员多模组时取对**本 TAG** 有增强的模组，档位按**绝对贡献**取最高有帮助档（不得因更高档拉低比值而改取低档）；持特限证章者：通用线与特限线**分别计算**、UI 分别展示且**特限线优先展示**（见 `docs/ui-render-rules.md`）、无特限证章者默认各模组增伤条件均满足、取更高者并把达成条件写进条件（不同 TAG 各行可分别取不同模组）；不用「更佳/可选」类模糊写法，模组无关于本 TAG 者不写。
- 「条件/备注」的完整标准与反例、正例见 `docs/concept.md`「结果展示」「条件分条」「备注分块」三节（本文件不再复述）；生成器 `tools/generate_results.py --check` 的文本 lint 会逐条列出不符规范的存量行。

## 4. 分文件形态（tag-part/1 JSON；改分文件一律经 `partdoc`，勿手写文本）

分文件是结构化 JSON：`body` 按文档序排出 `heading`（原文标题行）、`p`（散文/引用/空行的原文行）与 `table`（`columns` + `rows`＝单元格数组）三类元素；成员表行即 `rows` 里的一条单元格数组（列序看该表 `columns`，如 `干员｜编号｜[子 TAG／范围]｜条件｜备注｜依据`）。骨架：

```json
{
  "format": "tag-part/1", "kind": "player", "num": "13", "name": "高档控制", "title": "# 高档控制",
  "body": [
    {"t": "p", "lines": ["> 依据：…"]},
    {"t": "heading", "level": 2, "text": "## 评定标准"},
    {"t": "p", "lines": ["**纳入**：…", "**排除**：…"]},
    {"t": "heading", "level": 2, "text": "## 成员表（按实装时间倒序）"},
    {"t": "heading", "level": 3, "text": "### 大力推拉"},
    {"t": "table", "columns": ["干员", "编号", "条件", "备注", "依据"],
     "rows": [["温蒂", "char_400_weedy", "精英2；1或3技能专精3", "…（含数值/隐藏机制）", "温蒂/温蒂.md:54,61"]]},
    {"t": "heading", "level": 2, "text": "## 边界与排除记录"},
    {"t": "p", "lines": ["- 纳入存疑（未进主表）：<干员> —— 原因"]},
    {"t": "heading", "level": 2, "text": "## 待开发者确认"},
    {"t": "p", "lines": ["- <问题>（附证据与两种处理）"]},
    {"t": "heading", "level": 2, "text": "## 检索记录"},
    {"t": "p", "lines": ["- 关键词/正则：……（命中 N 文件 → 人工复核 M 人）"]}
  ],
  "trailing_newlines": 1
}
```

- 读写与校验：`partdoc.load(path)`（结构自检）／`partdoc.save(doc, path)`（原子写、CRLF、规范排版）／`partdoc.render(doc)`（还原 md 文本）。
- 单元格：单行、不得含 ASCII 竖线 `|`；`｜`（全角）用于备注分块。

### 排序与时间
- 成员表按**实装时间倒序**（新→旧）。上线时间从 PRTS `## 获得方式` 表格 `上线时间 | YYYY年M月D日` 提取；同日的按干员名拼音/原表顺序稳定排序即可。
- 依据列写 `文件:行号`（相对 `material_datas/PRTS/`，多行用逗号分隔），必须真实存在。

## 5. 检索与效率建议

- 用 Grep（ripgrep，支持中文）全库检索关键词/正则，再用 Read 带 offset 精读命中段；技能区在 `## 技能` 与 `## 后勤技能` 之间，天赋区 `## 天赋`–`## 潜能提升`，模组 `## 模组` 起。
- 技能表很长（每技能 13 行），优先读 **Rank Ⅲ（专精3）**与 **7 级**行，以及"备注(※)"行（隐藏机制多在此）。属性表在 `## 属性`。
- 交叉锚定：先用 `final_lists.tsv` / `merged.json` 缩小候选（如"为他人回复技力"=E_charge），再逐一回 PRTS 核对；官方 TAG 名单不全时以 PRTS 全库检索补全。

## 6. 质量要求

- **宁缺毋滥、宁标待考不硬判**：每条成员都要能落到 PRTS 原文；证据不足的进"边界与排除记录"或"待开发者确认"。
- 同名干员/召唤物、异格（如 凛御银灰 vs 银灰、怒潮凛冬 vs 凛冬、凯尔希·思衡托 vs 凯尔希）不得混淆。
- 完成后在回复中给出：文件路径、成员数、最重要的 3 条不确定点。
