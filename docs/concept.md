随着明日方舟干员机制的日益复杂，亟待一个更符合玩家需求的干员筛选系统。无论是游玩多年的老玩家，还是新入坑的新玩家，都可以通过这个筛选系统更好地了解各种干员的特性。

## 数据来源
PRTS

## 数据获取计划
将PRTS上的每一个干员页面，包含干员信息主体（以及可能具有的召唤物）的部分爬下来，存到这个项目的material_datas\PRTS里，每个干员具有一个单独的文件夹来存放其内容，因为有的干员具有召唤物，干员和召唤物信息分别提取到两个文件中，存放在同级目录里。

## 注意
在爬取PRTS的时候，需要注意爬取频率，避免触发限流机制。

# 筛选方式
不再通过传统的职业、分支等指标筛选（但是可以通过稀有度筛选），而是通过干员的“机制”进行筛选。这个机制可以是人为定义的。
例如说，筛选TAG有“造成弱点伤害”、“造成元素伤害”、“造成元素损伤”、“帧级结算（帧伤）”、“施加晕眩”、“自身重部署”、“传送敌人”等等，是写在干员的天赋、技能、模组里的信息，而非表面上展现出来的标签。
TAG之间也有层级之分，例如顶层TAG“造成元素损伤”下，有子TAG“造成神经损伤”、“造成灼燃损伤”、“造成凋亡损伤”、“造成侵蚀损伤”。（现行客户端官方另有第五系“狂躁损伤”，但目前没有任何干员施加它，故不设子 TAG。）
除了层级之分之外，还有更进一步的数值筛选，就拿“施加寒冷/冻结”为例，每个干员可以施加多长时间的寒冷？如果进一步施加寒冷，使其转变为冻结，或是直接施加冻结，又可以施加多久？还有的，对于施加晕眩，也有多种施加方式，是“技能期间间歇性的持续施加（例如佩佩）”、“天赋普通攻击概率施加（例如卡达）”、“天赋一次性施加（例如U-Official）”、“技能期间整段晕眩（例如缪尔赛思）”等。诸如此类。这类标准会非常多，因此大多靠人工拟定，但可以按照开发者的需求，让AI来设定开发者可能没有考虑到的部分。目前的考虑是，如果是官方定义的子TAG（例如元素损伤），设定为可筛选的TAG，如果是施加的方式（干员程序实现上的差异）的不同，改为标注在备注里，而对于类似的程序实现方式，可汇总一套一致的备注标注模板。
同级间的TAG可以属于同一类别，例如“施加晕眩”、“施加寒冷/冻结”、“传送敌人”都属于“控制”类别。
同级间的TAG需要按实装时间倒序排序，新机制往往和新干员匹配，有些机制是很老的干员就有，而有些机制是随着新干员的实装同步推出的。
同一个TAG下的干员同样按实装时间倒序排序，不过提供排序选项，让用户在正序和倒序中灵活切换。
用户可选的筛选TAG会非常之多，因此还需要有一个模糊搜索框来筛选“筛选TAG”，用户再从筛选出的筛选TAG里选择TAG来筛选出自己想要的干员。
对于官方设定的TAG，备注里引用游戏内文本作为证据；对于玩家体感类TAG，备注里写该干员在该TAG下能够为玩家的战术提供哪些帮助。
一个干员可能有多个TAG，而每个TAG都需要有自己的条件和备注。

# 结果展示
用户通过多选筛选TAG来筛选出想要找的干员，被筛选出的干员会展示这些信息：
基本信息：干员名称、职业、分支、稀有度、势力、实装时间。
条件：要具备TAG所描述的能力，需要什么样的条件，例如某些干员精二才能解锁具有相应TAG能力的天赋、技能或是模组，若干员在精零1级状态下就具有相应TAG所描述的效果，则填“无”。
备注：任意值得提的内容，范围不限，可以为空，最好写信息加工、筛选后有用的内容，或是特殊隐藏机制，亦或是为了帮助说明写的具体数值，不要写直接就写在干员信息里明晃晃的内容，那样玩家在游戏内直接看不就得了；举个例子，玩家体感TAG“决战歼灭”里的干员维什戴尔，虽然特性里写了是对地，但是三技能期间是具备对空索敌的，这点在游戏内文案无法直接看到，就可以写进备注里。

备注撰写的深层标准（与 docs/player-tags-specify.md 中各 TAG 的判定写法一致）：**条件**字段放硬性达成条件（精英化、模组等级、特殊需求等），**备注**字段放加工后的信息——隐藏机制、特殊用法与具体数值，二者分工明确。凡玩家凭直觉即知、或在游戏内文案一眼可见的内容不写备注。反例：迷狂牢笼不占用部署位是玩家下意识的认知，不必写；值得写的是它的特殊机制“可以阻挡本格内所有可阻挡的敌人”（与属性表阻挡数 0 并存，文案不易直接看出）。对于具体数值，若是PRTS文档里明写了，可以写；AI 通过计算得出的数值也可以写——计算规则已全部确定，**推算值不再加「（待验证）」字样**。另按各 TAG 要求，备注给出规定成绩项：决战歼灭＝15 秒窗口总伤与平均 DPS；次数对策＝等效每秒段数（见 `docs/calc-rules.md` §4.8）。模组类的隐藏机制（PRTS 在模组效果格里标 `※` 的补充说明，如距离增伤的门槛格数）查 `docs/module-hidden-mechanics.md`。

备注为**自包含文本**：不得以「见某干员条」「同上」「同格另一条」「另见某文件」等方式引用其它条目或文件，重复内容也要各写全。（规范源指针与PRTS证据行号除外。）

备注的**成绩前置**：同一干员在某 TAG 下存在多种情形的成绩时（例如可通过溢出机制把超额资源转化为输出者，或本体即达标、而召唤物／装置／特勤等附加因素可再提高成绩者），应把各情形的成绩列在**备注开头**（先列成绩、再展开细算），便于读者快速定位重点。

## 条件分条

**条件**按 `；` 分成各条**并列要求**，结果 JSON 里保持单字符串、前端逐条渲染，因此 `；` 只能切在并列要求之间：「或」的两支不要用 `；` 拆开，合并成一条、支内用 `／`——写 `精英1＋2技能 ／ 精英2＋3技能（专三数值）；潜能3`（两条：前一条是「或」，后一条是并列的潜能要求），不写 `精英1；2技能 ／ 精英2；3技能；潜能3`（会被切成三条、读成错误的并列）。同一条内的限定写进 `（）`，例：`精英2；3技能专精3（打数3→4）；X模组1级（特性追加）`。

**条件不写计算口径**：面板档位、计数方式、目标按几名计这类演算前提属于备注的「说明」块，条件只留硬性达成要求。

**条件性增伤的前提写进条件**：需要自身／目标处于某状态（在场时长、精力充沛、凝神、高生命值、处于元素爆发期间、剩余生命值低等）或布阵／数量条件（范围内存在其他我方干员、周围 8 格每个友方+X%、范围内敌人越多伤害越高）才生效的增伤，按 `docs/rulings.md`「条件性增伤一律折入」条把该前提写进条件（它属「能力成立的条件」、不属演算前提），数值取该条件满足时的值并在备注的「说明」写明来源与前提。

**条件不设字数上限**：条件的长短由**格式化**保证可读性——按 `；` 分条、并列要求合并成条、限定写进 `（）`；该写的硬性前提与硬性条件一个都不能为压字数而省（`docs/rulings.md`「条件不设字数上限」）。

## 备注分块

备注由若干**块**顺序组成，顺序固定为 **成绩 → 各能力块 → 计算 → 说明**。源单元格内一律单行书写，块与块之间用全角竖线 `｜`（U+FF5C）分隔；**ASCII `|` 会破坏表格结构，不得使用**。

| 块类 | 标签写法 | 条标签写什么 |
|---|---|---|
| 成绩 | `成绩`，或 `成绩 <情形名>（<面板口径>）` 如 `成绩 最低可满足档（精英1 满级＋满信赖＋潜能3）`、`成绩 完全溢出` | 技能名（`2技能`／`3技能`） |
| 能力 | 能力全称，见下 | 维度词（`持续`／`范围`／`伤害`／`打数`／`其它` 等） |
| 计算 | `计算` | 技能名 |
| 说明 | `说明` | 可省略 |

- **成绩块**：一个情形一块（双档、双情形、模组两条线各一块），情形名与面板口径写在块标签里；成绩项按各 TAG 的规定（决战歼灭＝15 秒窗口总伤与平均 DPS）。**能力块**：按 特性 → 第一天赋 → 第二天赋 → 技能（1→2→3）→ 模组 → 召唤物／装置 的顺序一块一个能力，标签写全称——`2技能「重力自定义」`、`第一天赋「飘浮大地之上」`、`模组「X」3级`、`召唤物「棋子」`；**不得写 `S2`、`2技能` 这类不点名的简写**。**计算块**放演算式与推导，与成绩块分开；**说明块**放口径、勘误与本 TAG 判据相关的边界说明（无关能力的「未计入」项不写）。
- 块内用 `；` 分**条**，条内用 `、`／`，` 连接元素。三个层级共用同一句法 `标签：正文`：块标签渲染为块标题，条标签渲染为行内键（`持续：22 秒`、`伤害：攻击力+165%…`）。条标签只在 ≤12 字且不含 `（）「」，。、` 时成立，否则整条作正文。
- **`｜` 与 `；` 在括号内不作分隔符**：`（）`／`「」`／`【】` 里的 `；` 是括号内容的一部分（如 `（最低可满足档 面板433×…；最高档 面板535×…）`），不会把一条拆成两条。因此括号必须**成对**——半角 `)` 也能闭合全角 `（`，但落单的 `（` 会让其后所有分隔符失效；`generate_results.py --check` 的文本 lint 会报「括号／引号不配对」。
- **块标签不会以 `「` 开头、也不含 `，`/`；`/`。`**：`「…」：…` 是引文正文而不是能力名，不会被当成块标题；能力块的标签一律是能力名（`2技能「重力自定义」`、`第一天赋「飘浮大地之上」`、`召唤物「棋子」`、`特性`）。
- 一条备注里的同一能力只写一块；同一能力的不同维度写成该块下的多条。

**只写与本 TAG 相关的信息**：条目只写**本 TAG 评定对象**直接成立的成绩、能力与算式——与该评定对象无关的能力（特性、别的天赋、别的技能、与本次取用无关的模组线）不写成能力块，与本次纳入无关的演算也不写进 `计算`。**被实际纳入计算的部分照留**（面板组成式、倍率链、该能力本身的口径与前提）；与本 TAG 判据同源、需说明「为何不计」的边界项仍写进 `说明`，其余「未计入：X」不写。判据是「这与本 TAG 判的这件事有关吗」，不是「顺便交代一下」；**符合本 TAG 判据的能力一项都不能漏**（见下「数值可复算」与各 TAG 的评定标准）。

**能力块自足**：每个能力块必须有一条说明**该能力本身**——触发条件、作用对象、效果；数值影响另起一条。禁止只写「对主目标提升至 125%」「触发率提至 100%」这类脱离主语的片段：每个数值都要能看出它属于哪个对象、在什么条件下成立（含它属于技能还是天赋——技能追加的效果写在技能块里，不要挂到天赋块上）。

**数值可复算**：`计算` 块首条写**面板组成式**——`面板855＝精英2满级671＋满信赖+90＋潜能4攻击+27＋Δ模组3级攻击+67`，其后写倍率链与取整；`成绩` 块标题里的档位注记必须与条件、与本组成式一致。面板由 `prts_stats.py` 复算（属性表＋信赖＋潜能＋模组档位固定属性），不要手抄。概率项按期望计并写出算式（不得按「每次攻击触发 1 次」这类未声明假设）。**未计入项不再逐条写进 `说明`**——只写与本 TAG 判据同源、需说明「为何不计」的边界项；`verify_numbers.py` 的因子覆盖清单仅供写手自查（不再是产物要求）。

**成绩只允许三种情形并列**：① 条件只要求精英0／精英1 即可满足 TAG 要求时，给「最低可满足档／最高档」两套；② 特殊机制带来的多情形（如「完全溢出／完全不溢出」）；③ **模组的两条线**——持特限证章者，通用线与特限线分别计算、各列一块成绩，特限线在前（情形名写法见 `docs/ui-render-rules.md`「模组两条线的展示」）。**其余一律取满配档**、单套成绩；同一线内的模组取舍（取哪档、为何不取）在 `计算` 里写清（不并列为成绩）。

**内部代号不入产物**：攻击范围代号（`代号 3-18`）、复算规则号（`R7`）、分文件名（`08-拐杖.md`）、子表号与路径号（`表 2A`／`路径⑤`）、技能简写（`S1/S2/S3`）、英文模组码（`HOK-Y`）一律改写为产品可读表述——攻击范围只写「N 格／最远 N 格」＋必要时形状描述，模式限定模组写「集成战略／生息演算／岁的界园志异 特限模组」，模组线写 `X模组1级`／`Y模组3级`。代号只留在分文件的「依据」列。
- 源单元格是**表格单元格**：不得含换行、不得含 ASCII `|`，选项之间用 `／` 表「或」、`；` 表分条。生成器会把 `｜` 与 `；` 解析成结果 JSON 的块数组与条数组（结构见 `docs/output-standard.md` §4.2）。

**不得出现在备注中**（生成器 lint 会报告）：`★` 作分类标记（`★` 只允许出现在星级写法 `N★` 中）；`备注：`／`PRTS 备注：`／`PRTS 注：`／`天赋原文`／`技能原文` 等前缀字样（内容照写，不加前缀）；`（下详）`／`见备注` 等指向其它条目或本条目别处的悬空引用（自包含写全）；面向 UI 的指令文字；`文件:行号` 证据（一律写进「依据」列）。

`generate_results.py --check` 的文本 lint 同时做**结构检查**——括号是否配对、`；`／`｜` 是否连写产生空条、以 `成绩`／`N技能`／`第一天赋` 等开头的块是否真的被识别为块标签（标签过长或含句读会被退回正文，属静默失格式）。结构问题是静默的，必须由 lint 兜住；重排过的行另由 `audit_text_migration.py` 查数字与依据守恒（**有意改动的数字必须登记进它的 `ACCEPTED` 并写明理由**，每加一条即一次显式裁定）；数值本身由 `verify_numbers.py` 对着 `prts_stats.py` 复算的面板校准（面板是否与声明档位相符、模组档位是否取满、恒等式是否成立、该干员的因子是否都被点到）。

对于“荐”的标注，AI可以给出推荐建议，但实际标注必须由开发者人工来。荐的意义在于标注出某个玩家体感TAG下，效果显著高于其他干员的干员。例如对于“次数对策”TAG，我不知晓维什戴尔2技能期间总共会造成多少段伤害，但我知道在她能造成的伤害段数的量级一定是远在赤刃明霄陈3技能之上的，那么AI就可以推荐将“荐”赋予维什戴尔。

# 项目职能
本项目只做干员TAG分类和生产分类结果json的事情，不做UI上的显示，UI上的显示是另一个项目的事情。本项目要做的就是产出结果json，将之复制到另一个项目中映射为UI，供用户们筛选。
本项目仅产出2份json，存放到results目录里：
1. 干员TAG分类结果json，包含官方设定TAG和玩家体感TAG下的所有干员。TAG和干员之间是多对多的关系。每个干员具备的每一个TAG，都需要有一个条件和备注。
2. 战斗术语json，已存放于results\combat_glossary.json。

# 干员特性分析
干员数量太多，需要使用AI模型来帮助分类，但是AI模型并不一定清楚明日方舟的伤害计算、状态施加机制，因此在遇到不能绝对确定的地方时，一定要使用ASK功能向开发者求证。
