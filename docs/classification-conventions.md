# 分类约定与评定标准写法

> 用途：给条目写「条件」「备注」时遵守的约定，以及评定标准本身的撰写规则。官方设定 TAG 与玩家体感 TAG **通用**。
> 开工时**不必读本文**——按 `AGENTS.md` §一 取开工件；写条目时按需查本节。

## 一、分类约定

- **证据制**：一切判定引用 `material_datas/PRTS/` 下的 `文件:行号`；**不得凭模型记忆判定**。不确定的标 `[待考]`，转进目标文件自身的 `## 待开发者确认`。

- **条件 vs 备注**：条件＝硬性要求，备注＝加工后的信息（数值、时长、隐藏机制、战术用法）。完整规则、反例与正例在 `docs/concept.md`「结果展示」，照它执行、不要在此重述。两者的**排布规范**同在该文件：「条件分条」（`；` 只切并列要求，「或」合并成一条、支内用 `／`）与「备注分块」（`｜` 分块、`；` 分条、两层都用 `标签：正文`；块序 成绩→能力→说明；`★` 分类标记与 `备注：` 类前缀禁用）。源字段（分文件 JSON 的「备注」列值）里用 `｜` 写，生成器解析成结果 JSON 的块数组；不符规范的行由 `tools/generate_results.py --check` 的文本 lint 逐条列出，改动过的行另跑 `.claude/skills/tag-batch-rewrite/scripts/audit_text_migration.py`（数字守恒／依据不丢）。

- **数值取自机读层、不手抄**：面板（满信赖＋最高精英满级＋有效潜能最高档＋条件点名模组档位固定属性）、潜能与模组各档固定属性的**唯一取数处**是 `agent_workspace/tag_pipeline/stats.json`（`tools/prts_stats.py` 从 PRTS 语料抽取，`panel_of()` 给面板与组成式）；产物里的每个 `面板NNN` 由 `tools/verify_numbers.py` 回头校准。

- **档位取用**：模组／潜能取对本 TAG 有帮助的最高档并写进条件。**「有帮助」按绝对贡献判**——不得因更高档会拉低比值／稀释均值而改取低档；多条通用模组之间平权、取成绩更高者；持**特限证章**者通用线与特限线**分别计算**、UI 分别展示且特限线优先；无者默认模组增伤条件均满足、取更高者并把条件写进条件（见 `docs/rulings.md`）。

- **计算规则只作用于玩家体感 TAG**——官方设定 TAG 不涉及计算部分。

- **成绩并列只允许两种**：「精英0/1 可满足的最低档＋最高档」与「特殊机制多情形」；其余取满配档。能力块必须自足（写清该能力本身）。

- **未计入项写进 `说明`**（只写与本 TAG 判据同源、需说明「为何不计」的边界项）。

- **内部代号不入产物，模组代号例外**：范围代号、`S1/S2/S3`、`表 2A`、`路径⑤` 一律改写成人话；模组代号**必须进**，统一写「中文线名（代号）」如 `X模组3级（HOK-X）`、`集成战略特限模组3级（ISW-α）`（见 `docs/rulings.md`「模组代号进产物」）。

- **默认敌人是纯木桩**：0 防御／0 法术抗性／0 闪避免伤／无任何减伤。作用于敌方防／抗**数值**的减益与穿透**不计入**；作用于**承伤倍率**的增伤（脆弱、通缉）**照计**。

- **不丢能力**：某干员的条目必须列出**每一项**符合该 TAG 评定标准的能力——多项合格特性全部写出（条件覆盖每项硬性要求，备注逐条列出）；不得因为重叠、较小、或已写了更强的一项而省略。

- **不多写无关内容**：条目只写属于该 TAG 评定对象的东西——其它能力（特性／别的天赋／别的技能／未取用的模组线）连同其「未计入」注記都不写；**实际折入计算的部分照留**（面板组成式、算式）。见 `docs/rulings.md`「条目只写与本 TAG 相关的内容」与 `docs/concept.md`「备注分块」。

- **召唤物／装置算持有者的能力**；**模式限定模组（ISW-α／RA-α 等）计入**玩家 TAG——条件写明模式限定，备注注明仅该模式可用。

- **方向重要**（对友方 / 对自身 / 对敌方）；一名干员可属**多个 TAG**；玩家 TAG 可有**子 TAG**（实现方式／类型／范围之别）。

- **只写机制层、与时间无关的判断**：不写强度榜／当期环境结论。

- **成员表按实装时间倒序**（日期取自 PRTS `## 获得方式`，缓存在 `player_tags/_launch_dates.json`）；边界／组合表按各自分组。

- **改任何玩家 TAG 前，先读目标文件自身的「评定标准」与「边界与排除记录」**；开发者的裁定与开放问题落在各分文件自身的 `## 待开发者确认`。

- **玩家 TAG 作业用并行代理**：一 TAG 一代理，写出带证据的分文件于 `player_tags/`，遵循 `_brief.md`；合并脚本汇总成 `docs/player-tags-members.md`（剥离「依据」列）。证据留在分文件里。

- **新增 TAG**：按 `.claude/skills/add-player-tag/SKILL.md` —— 在动任何成员前，先与开发者把评定标准说清；除非开发者明确选择「先创建此 TAG、评定标准后续更新」的 stub 方案。

- **评定标准只给了几个例子／模糊表述**（「相当高」「较强」）时：按 `.claude/skills/solidify-criteria/SKILL.md` —— 回源枚举同类与边界样例 → 逐条请开发者裁定 → 提炼可量化标准 → 样例回归验证；对外释义（tooltip 等）同步更新。

- **新干员实装**（开发者给出 PRTS 链接或描述）：按 `.claude/skills/add-new-operator/SKILL.md` —— 爬取进 `material_datas/PRTS/`（含攻击范围）、逐 TAG 判定（官方＋玩家）、就问没有 TAG 覆盖的显著机制，然后只更新成员文档（`docs/official-tags-members.md` ＋ 分文件 → 合并文档）——**绝不生成** `results/operator-tags.json`。

- **版本更新**（新干员＋既有干员新模组，增量）：按 `.claude/skills/update-version/SKILL.md` —— 只刷新变更的干员、把新模组折进受影响的行（模组档位）、跑跨干员影响清单（新阵营成员／使能者／对外挂点…）；**绝不整表重扫**。

## 二、评定标准写法规则

- **术语**：一个 TAG 的评定标准就叫 **评定标准**——小节标题（`## 评定标准`）、其子标题、以及任何陈述／引用／记录标准的正文都用这个词。**两套 TAG 体系皆然**：官方条目（`docs/official-tags-members.md` §1/§4）与每个玩家 TAG 文件（`agent_workspace/tag_pipeline/player_tags/NN-*.json`）。**不要**用 口径、裁决 或任何同义词指代标准本身；子规则（如何计数、如何取整等）用朴素词——计数方式／计算方式／判定／门槛——绝不用「口径」。

- **不盖日期、不留编辑痕迹**：新增、修订或移除标准时，**绝不要**打日期或轮次标记（`2026-09-11`、本轮、追加、最新、二次更新…），也不要把编辑动作写进正文（不写「覆盖上一轮…」「已落实」「重新纳入」「移出改为…」「修正后」这类前后对比措辞）。读者不能从文本看出某条规则来自哪一轮。

- **每条评定标准必须清晰、有序、整洁、风格一致**：
  - **清晰**——纳入写「收什么」，排除写「不收什么」，判定阈值与算式给全；
  - **有序**——固定顺序：规格原文（如有）→ 纳入 → 排除 → 与其它 TAG 的关系 → 通用约定（数值档位、召唤物／装置、模式限定模组）；有子 TAG 时每个子 TAG 独立成块、用同一套小标题；
  - **整洁**——不重复、不夹叙旧账、除本文件其它小节编号外不引用「第几条」；
  - **风格一致**——统一用 `**纳入**：`、`**排除**：`、`**与其它 TAG 的关系**：`、`**约定**：` 等加粗标签起头。

- **折入结构**：把新标准折进既有结构——它所属的路径、成员表、边界记录——然后**通读该 TAG 的整节评定标准并整理**：合并冗余、重编路径号、改写措辞，使其读起来像一次写成的干净规范。

- **边界／排除／待开发者确认记录**只陈述规则／事实及其理由，**不是名单演变的变更日志**（同样去掉本轮／日期／「已落实」类标记）。**检索记录**是唯一允许保留带日期的过程记录的地方。
