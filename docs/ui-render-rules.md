## 1. 数据接入

| 项 | 约定 |
|---|---|
| 文件 | `results/operator-tags.json` + `results/combat_glossary.json` → 原样复制进 UI 项目的 `src/static/json/combat/` |
| 加工 | **无**。前端不做任何数据改写、裁剪或补全 |
| 载入 | 页面挂载时动态 `import()`：1 MB 的 `operator-tags.json` 被构建工具拆成独立异步 chunk，不拖累其它路由；载入中显示 loading，失败显示错误信息（失败时整页只有提示，不降级渲染） |
| 术语文件 | 只用于 §7 的注释文本内联标注，不参与筛选与检索 |

> 复制是**每次重新生成后必须做的一步**：页面只认 `src/static/json/combat/` 里的副本，源项目改了 `results/` 而没重新复制，前端表现不会有任何变化。
> 截至 2026-09-25：两份副本均已同步（`operator-tags.json` v4；`combat_glossary.json` 11 节 119 条）。此前术语副本曾长期停留在 5 节 65 条的旧版，导致新增的 54 个术语不被标注 —— 这类"漏复制"不会报错，只会静默少标注，建议每次重新生成后都对一遍 md5。

## 2. 字段用途一览

### 2.1 `operators[]`

| 字段 | 前端用途 | 缺失/异常时 |
|---|---|---|
| `name` | 干员区列表的唯一来源；全部索引的键（成员条目、荐名单、提供者头像都按名字关联） | 不在 `operators[]` 里的干员**不会出现在干员区** |
| `charId` | 头像组件入参、卡片 key | 无头像；重复会让卡片互相顶掉 |
| `rarity` | 头像描边、星级文字（`★` 重复 rarity 次） | 头像按 6 处理 |
| `class` / `branch` | 卡片与详情副标题（`职业·分支`） | 缺失则该项为空 |
| `faction` / `releaseDate` | `faction` 仅详情卡片展示（`势力 · 日期 实装`）；`releaseDate` 还用作 §5.2 里组合提供者的排序键 | `faction` 缺失则整段省略；`releaseDate` 缺失则该提供者排在其所属分组的末尾 |
| `prtsUrl` | 详情卡片的外链 | 缺失则不渲染链接 |

### 2.2 `tags[]`

| 字段 | 前端用途 | 缺失/异常时 |
|---|---|---|
| `id` | 选择状态、全部索引的键；**`P12` 被硬编码识别为「阵容组合」维度** | — |
| `name` | TAG chip 文案、荐标识的悬浮提示 | — |
| `source` | 分成「官方设定 TAG」「玩家体感 TAG」两块；**荐资格只认 `player`** | — |
| `category` | 官方 TAG 的分组小标题（现状 9 类，按 JSON 顺序） | 按「其它」归组 |
| `members` | 筛选与详情的全部数据源 | 空数组合法 |
| `recommended` | 荐名单 | 缺省视为空数组（官方 TAG 现状无此字段） |

### 2.3 `members[]`

| 字段 | 前端用途 |
|---|---|
| `operator` | 干员名（非阵容组合 TAG） |
| `condition` | 详情卡片的「条件」行；字符串，前端按 `；` 拆成逐条 chips（单条时不拆）。写法见 `docs/concept.md`「条件分条」 |
| `remark` | 详情卡片的「备注」行，**块数组** `{label?, items:[{label?, text}]}`（结构见 `docs/output-standard.md` §4.2、渲染见 §6.3）。另参与 §7 术语标注（只标注 `text`，不标注 `label`），并被用作组合卡片摘要（取首块首条、截断 96 字） |
| `subTags[].group` / `.value` | 子 TAG 筛选项，前端只做 `{group, value}` 去重与精确匹配，不解释语义 |
| `prtsUrl` | 条目级外链 |
| `combo` | **P12 专用**：组合名（同一 TAG 内要求唯一，前端以它为 key） |
| `providers[]` | **P12 专用**：提供者（`operator` / `condition` / `remark` / `prtsUrl`）；只有 `operator` 会用于取头像与星级 |
| `beneficiaries[]` | **P12 专用**：受益者名字，只渲染成纯文字 chips，**不取头像**（可以不在 `operators[]` 里） |

## 3. 索引（页面打开时构建一次，之后全是查表）

| 索引 | 内容 | 说明 |
|---|---|---|
| `tagById` | `tagId → Tag` | — |
| `officialTags` / `playerTags` | 按 `source` 分组 | 保持 `tags[]` 顺序 |
| `officialByCategory` | 官方 TAG 按 `category` 分组 | 组序＝首次出现顺序 |
| `opEntriesByTag` | `tagId → 干员名 → 条目[]` | **跳过 `P12`**（组合条目没有 `operator`）；同一干员在同一 TAG 下的多条条目会聚合在一个数组里 |

| `recSets` | `tagId → Set(荐名单)` | — |
| `recTagIdsByName` | `干员名/组合名 → 荐它的 TAG id[]` | 由 `recSets` 倒排，避免逐张卡片重复扫描全部 TAG |

| `p12Combos` | `P12.members` 中带 `combo` 的条目 | 已按 §5.2 的组合顺序排好 |
| `providersCharId` / `providersRarity` | `干员名 → charId / rarity` | 由 `operators[]` 建，用于组合卡片的提供者头像 |

## 4. 筛选规则

### 4.1 多选 TAG ＝ 交集（AND）

干员必须出现在**每一个**已选 TAG 的成员里（对非 P12 的 TAG 判定）。官方设定 TAG 与玩家体感 TAG 同等参与，不做区分。

### 4.2 子 TAG ＝ 与 TAG 同为交集（P12 的子项除外）

选中某个 TAG 后，其下展开该 TAG 的 `subTags` 去重选项：

- **多选取交集**：该 TAG 下勾选多个子项时，干员须**逐项命中**——对每个已选子项，该干员在该 TAG 下都存在一条带有该子项的条目（可分散在不同条目上；例如同时勾选「物理闪避」与「可给予他人」，可由同一 TAG 下的两条不同条目分别命中）；
- 子项与 TAG 本身仍是 **AND**：先满足该 TAG 的成员资格，再看子项；
- 不勾任何子项 ＝ 该 TAG 不限子项；
- **例外（P12）**：阵容组合的子项＝组合名，多选时展示所选的那几个组合（并集语义），不适用本条。

命中判定看的是**条目级**的 `subTags`，因此"同一 TAG 内多条条目、末端子 TAG 不同"的情况会自然被覆盖（例如结城理在「闪避」下同时带 `物理闪避`、`法术闪避` 两条子 TAG）。

### 4.3 名称搜索

对**干员名**与**组合名**做子串匹配（不区分大小写），与 TAG 筛选同时生效（AND）。搜索不检索条件、备注、子 TAG 文本。

### 4.4 「阵容组合」（P12）只能单独选择

- 点选 P12 时：清空其它全部 TAG 选择与其子项；
- 已选 P12 时点选任何其它 TAG：取消 P12。

因此 P12 永远不与其它 TAG 共存，UI 上以**虚线描边 + 紫色文字 + 图标**标识，悬浮提示「仅可单独选择」。

### 4.5 结果区的划分

| 情形 | 干员区 | 组合区 |
|---|---|---|
| 未筛选 | 全部干员 | 不展示 |
| 只选了 P12 | **不展示**（避免"组合→全部干员"的空降噪音） | 全部组合卡片（顺序见 §5.2） |
| 选了非 P12 的 TAG | 命中交集的干员 | 不展示 |

两区互不互斥：P12 不参与干员区的交集判定，干员区只看非 P12 的 TAG。

### 4.6 空结果

两区都为空时显示「没有同时满足全部所选条件的干员/组合。」

### 4.7 干员区是窗口化的（一次只渲染 30 张）

- 干员区**不会把命中集全部塞进 DOM**：首屏渲染前 30 张，底部哨兵进入视口附近时再补 30 张，直到全部显示（哨兵文案会显示「已显示 X / N」，也可点击补页）。
- 统计行的「命中 N 名干员」始终是**完整命中集**，不是当前已渲染的张数。
- 结果区不在视口内时，筛选变化只更新命中集与统计数字，不重建卡片；滚回视口时补一次提交。这是"在筛选面板连点 TAG 不卡"的来源，不改变最终呈现。
- 组合区不窗口化（最多十余张，一次全部渲染）。
- 对源项目的影响：**命中数不等于 DOM 里的卡片数**属于预期行为，排查"某干员没显示"时先确认是不是没滚到底。

## 5. 荐的渲染

### 5.1 干员级「荐」

- **只认玩家体感 TAG**：未选任何玩家体感 TAG（含"只选了官方 TAG""未筛选"）时，一律不显示荐标识；
- **多选取交集**：同时选中多个玩家体感 TAG 时，干员必须出现在**每一个**已选玩家体感 TAG 的 `recommended` 名单里才显示；
- 官方 TAG 的 `recommended` 不参与（现状它们也没有该字段）。

标识为卡片右上角的**静态菱彩菱形**（旋转 45° 的方块，彩虹渐变，无动画），悬浮提示 = `荐：<TAG 名、…>（新手优先培养，仅供参考）`。

### 5.2 荐的排序（先荐后其余）

**干员区**：命中干员分两桶 —— 先追加「荐」的干员，再追加其余干员；**两桶内部都保持 `operators[]` 的原顺序**（不使用 `recommended` 的数组顺序，该顺序按 `docs/output-standard.md` §6 不含展示优先级语义）。没有荐时就是 `operators[]` 原序。

**阵容组合内（提供者）**：作用在提供者上的排序是**两级键** —— ① 带组员荐的排在前面；② 同一组内按该提供者的**实装时间降序**（新的在前）。实现取 `operators[].releaseDate`（`YYYY-MM-DD` 字符串直接比较）；缺失实装时间的排在该组末尾，同日或都缺日期时保持 `providers[]` 原顺序（排序稳定）。组合卡片的头像行是**先排序、再截断前 8 个**，因此带荐的提供者一定落在可见的头像行里；组合详情卡片的提供者列表用同一顺序。受益者 chips 不参与该排序（保持 `beneficiaries[]` 原顺序）。

**阵容组合本身（组合之间）**：同样两级键 —— ① 带组荐的组合排在前面；② 其余按 `operators[].releaseDate` 降序，**组合没有自己的实装时间，取“该组合最新提供者的实装时间”** 作为排序键（例如 S.E.E.S. 取 2026-09-04）。缺失/同日保持 `members[]` 原顺序。该顺序同时用于**组合卡片**与「阵容组合」下的**组合名 chips**（两处必须是同一顺序）。

### 5.3 阵容组合的「组荐」与「组员荐」

按 `docs/output-standard.md` §6「相互独立」的设定，前端**不复用干员级荐的判定**，而是直接看 P12 自己的 `recommended`：

| 概念 | 判定 | 展示位置 |
|---|---|---|
| 组荐 | 组合名 ∈ `P12.recommended` | 组合卡片右上角菱彩；组合详情卡片标题旁的菱彩 |
| 组员荐 | 提供者名 ∈ `P12.recommended` | 组合详情卡片中该提供者名字后的**小号菱彩图标**（无文字）；并参与 §5.2 的组合内排序 |

两者都**不因多选其它玩家体感 TAG 而消失**（P12 本身也只能单独选择）。组荐与组员荐互不派生：给组合加荐不等于给它的提供者加荐。

### 5.4 文案

页面固定展示四块说明：使用说明 / 关于「荐」（定义与判定方式）/ 阵容组合的荐（含"带荐优先练、不带荐但已打算练则优先练组内带荐干员"两条）/ 免责说明（主观评定、可能不完整、不构成抽卡建议）。文案写死在页面里，**不来自 JSON**；若 `docs/output-standard.md` §6 的荐规则调整，需要同步改页面文案与 `src/utils/seo.js` 里的页面描述。

## 6. 卡片与详情卡片

### 6.1 干员卡片

头像（按 `rarity` 描边）→ 名字 → 星级 → `职业·分支` → 命中的 TAG chips。

- 有筛选时，chips ＝ 命中的那些 TAG 名；
- 未筛选时，chips ＝ 该干员出现过的 TAG 名取前 4 个，多余显示 `+N`；
- 有荐时右上角菱彩。

### 6.2 组合卡片

组合名 → 提供者头像行（**组员荐优先，组内按实装时间降序**，见 §5.2；最多 8 个）→ `提供者 N 名 · 受益者 M 名` → 机制摘要（`remark` 截断 96 字，带术语标注）。

### 6.3 干员详情卡片

点卡片打开：大头像、名字（有荐则带菱彩）、星级、`职业·分支 · 势力 · 实装日期`、PRTS 干员页外链；下方按 TAG 分组列出条目。

**条目范围的规则**：

| 情形 | 展示哪些 TAG 的条目 |
|---|---|
| 有筛选 | 该干员**命中的那些 TAG**（非 P12） |
| 未筛选 | 该干员出现过的**全部 TAG** |

若某 TAG 下勾选了子 TAG，该 TAG 的条目会先按子项过滤：保留命中任一已选子项的条目——交集语义已在干员级判定，条目级取并集正好把每一条已选子项的证据都显示出来；过滤后为空则回退展示全部条目，避免空白。

每条条目展示 `条件` / `备注` / 子 TAG chips / 条目级 PRTS 外链：

- **条件**：字符串按 `；` 拆成逐条 chips（`无` 或仅一条时按纯文本渲染），`／` 的「或」语义留在同一 chip 内。
- **备注**：块数组按块类渲染，由块标签判定——`成绩`（或 `成绩 <情形名>`，标签以 `成绩` 开头）＝主色左边框＋淡底的高亮卡，情形名作副标题，条标签（技能名）作左列；其余标签＝能力块（色条＋主色标题，条标签为 `持续`／`范围`／`伤害`／`打数`／`其它` 等维度词，渲染为左列键，无标签的条占满整行）；标签为 `计算`＝**默认折叠**的「演算过程」，点击标题展开（内容仍在 DOM 中，仅视觉折叠）；标签为 `说明`＝小字灰色；无标签块＝普通段落。渲染是**键值对齐**：条标签列右对齐并带一条分隔竖线，同一块内的条共用列宽。
- 备注与条件的标签都**不参与术语标注**（避免标签被包成术语），标注只作用于正文。

**模组两条线的展示（特限／通用）**：持**特限证章**（模式限定模组）的干员，同一 TAG 条目下**通用线与特限线分别计算的两套成绩都要展示，特限线的成绩在前**——成绩块用情形名区分两条线：特限线写其模式（`集成战略特限`／`生息演算特限`／`岁的界园志异特限`），通用线写 `通用线`，各自的面板口径写在块标签的括号里；条件与「说明」把两条线各自的前提与取档并列写全（渲染与单线条目一致：块数组、键值对齐、`计算` 折叠）。若干员有**多个特限证章**：同模式的取更高者；不同模式的分别计算，并在特限优先的列表里按 **PRTS 模组页自上而下的顺序**依次展示（当前尚无此类干员）。

### 6.4 组合详情卡片

组合名（有组荐则带菱彩）、`阵容组合 · 提供者 N 名`、条件、机制（`remark` 全文）、受益者 chips（保持 `beneficiaries[]` 原顺序），然后逐个提供者列出（**组员荐优先、组内按实装时间降序**，见 §5.2）：头像 + 名字（有组员荐则带小号菱彩）+ 条件 / 备注 / PRTS 外链。长内容在卡片内滚动，底部「关闭」按钮固定。

## 7. 备注/条件文本内的术语标注

- 术语表来自 `combat_glossary.json` 的全部 `sections[].terms[]`，按 `name` 长度**降序**拼成正则（保证「凋亡损伤·我方」先于「凋亡损伤」命中）；
- 匹配前先做 HTML 转义（`& < > "`），因此**备注里可以直接写尖括号原文**（如 `<塔纳托斯>`），前端会按字面展示而不会被当成标签吞掉；
- 命中的词包成 `<span data-combat-term="术语名">`，渲染为**天蓝色 + 灰色下划线 + 手型光标**；
- 点击（事件委托）弹出浮窗：标题＝术语名，内容＝`definition` ＋ `notes` 列表；
- 标注单元是**条/块的正文 `text`**（以及条件的每个 chip），块标签与条标签不参与匹配。

## 8. 前端对 JSON 的隐含约定（改数据前逐条核对）

| # | 约定 | 现状 | 破坏后的表现 |
|---|---|---|---|

## 9. 源项目改动时的自检清单

改完 `results/operator-tags.json` 后，按改动类型快速过一遍：

1. **新增/移动成员或提供者** → 确认该干员在 `operators[]`（约定 1）；确认 `condition` 写全硬性前提（详情卡片直接展示原文，并按 `；` 拆条渲染，故 `；` 只能切在并列要求之间）。
2. **新增/改子 TAG** → 无需改前端，`subTags` 组名与取值是自由的（约定 11）；**子 TAG 多选为交集，与 §4.2 一致**（前端的干员级命中判定与详情卡条目过滤都按该语义实现，改数据时对照本条）；若子 TAG 用于 `P12`，注意前端把 P12 的子项当作**组合名**处理，不要给组合条目加 `subTags`。
3. **改荐名单** → 干员级荐要满足"多选取交集"的展示语义：只在部分 TAG 有荐的干员，在选择多个 TAG 时会不显示（这是设计预期，不是 bug）。P12 的荐元素只能是组合名或该组合的提供者名（约定 8）。
4. **新增 TAG** → 给一个稳定、唯一的 `id`；`source` 取 `official` / `player`；官方 TAG 目前不带 `recommended`（约定 7）。若新增的 TAG 需要"只能单独选择"这类特殊交互，需要在 `docs/ui-render-rules.md` 与前端页面同时登记。**现状提醒**：新增了玩家 TAG `P13`（高档控制，子 TAG＝大力推拉／阻挡数5／长效控制／远距控制）；原 `P10`（大力推拉）、`P11`（阻挡数5）已**退役**——前端若存有以旧 id 记录的选择状态，需按 id 失效处理（退役 id 不复用）。
5. **改 `operators[]` 字段** → 对照 §2.1 确认前端用到的字段仍然存在。注意 `releaseDate` 不只是展示：它决定组合内提供者的排序（§5.2），改动或缺失会直接改变列表顺序。
6. **改备注文本** → 尖括号可以直接写（§7）；按 `docs/concept.md`「备注分块」的块序与块标签写，块类决定渲染样式（§6.3），故块标签不是自由文案；文本里出现的术语会自动加蓝色下划线并可点击，若某个词不该被当成术语，应改 `combat_glossary.json` 的术语表而不是改备注。
7. **改数据结构（字段改名、层级调整）** → 前端不会降级兼容，会直接渲染异常或整页报错，必须同步修改 `src/pages/tools/better-combat-operator-filter.vue` 与本文。
