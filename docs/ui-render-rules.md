# 结果 JSON 的前端渲染规则（「更好的作战干员筛选」页面）

> 编写：2026-09-18。
> 消费端：一图流前端项目 `frontend-v2-plus` 的页面 `src/pages/tools/better-combat-operator-filter.vue`（路由 `/tools/better-combat-operator-filter`，站内位置：一图流工具箱），数据取自 `src/static/json/combat/` 下的两份副本（与 `results/` 逐字节一致，不在前端仓库内手工维护）。
> 数据快照：`results/operator-tags.json`（v1 / 2026-09-17：398 名干员、93 个 TAG ＝ 官方 81 ＋ 玩家 12、1668 条成员条目、14 个阵容组合、26 条荐）＋ `results/combat_glossary.json`（5 节 65 条术语）。
> 定位：本文记录**消费端当前怎样读取与展示结果 JSON**，作为源项目后续改动的核对清单 —— 修改 JSON 结构、字段语义或名单规则时，对照 §8 判断前端是否需要同步。JSON 本身的格式规范见 `docs/output-standard.md`，荐的评定标准见其 §6，本文只讲"前端怎么用"。
> 维护：前端页面的渲染规则一变，本文同步更新。

## 1. 数据接入

| 项 | 约定 |
|---|---|
| 文件 | `results/operator-tags.json` + `results/combat_glossary.json` → 原样复制进 UI 项目的 `src/static/json/combat/` |
| 加工 | **无**。前端不做任何数据改写、裁剪或补全 |
| 载入 | 页面挂载时动态 `import()`：1 MB 的 `operator-tags.json` 被构建工具拆成独立异步 chunk，不拖累其它路由；载入中显示 loading，失败显示错误信息（失败时整页只有提示，不降级渲染） |
| 术语文件 | 只用于 §7 的注释文本内联标注，不参与筛选与检索 |

## 2. 字段用途一览

### 2.1 `operators[]`

| 字段 | 前端用途 | 缺失/异常时 |
|---|---|---|
| `name` | 干员区列表的唯一来源；全部索引的键（成员条目、荐名单、提供者头像都按名字关联） | 不在 `operators[]` 里的干员**不会出现在干员区** |
| `charId` | 头像组件入参、卡片 key | 无头像；重复会让卡片互相顶掉 |
| `rarity` | 头像描边、星级文字（`★` 重复 rarity 次） | 头像按 6 处理 |
| `class` / `branch` | 卡片与详情副标题（`职业·分支`） | 缺失则该项为空 |
| `faction` / `releaseDate` | 仅详情卡片展示（`势力 · 日期 实装`） | 缺失则整段省略 |
| `prtsUrl` | 详情卡片的外链 | 缺失则不渲染链接 |

### 2.2 `tags[]`

| 字段 | 前端用途 | 缺失/异常时 |
|---|---|---|
| `id` | 选择状态、全部索引的键；**`P12` 被硬编码识别为「阵容组合」维度** | — |
| `name` | TAG chip 文案、荐标识的悬浮提示 | — |
| `source` | 分成「官方设定 TAG」「玩家体感 TAG」两块；**荐资格只认 `player`** | — |
| `category` | 官方 TAG 的分组小标题（现状 9 类，按 JSON 顺序） | 按「其它」归组 |
| `members` | 筛选与详情的全部数据源 | 空数组合法 |
| `recommended` | 荐名单 | 缺省视为空数组（官方 TAG 现状无此字段） |

### 2.3 `members[]`

| 字段 | 前端用途 |
|---|---|
| `operator` | 干员名（非阵容组合 TAG） |
| `condition` / `remark` | 详情卡片的「条件」「备注」行；`remark` 额外参与 §7 术语标注，并被用作组合卡片摘要（截断 96 字） |
| `subTags[].group` / `.value` | 子 TAG 筛选项，前端只做 `{group, value}` 去重与精确匹配，不解释语义 |
| `prtsUrl` | 条目级外链 |
| `combo` | **P12 专用**：组合名（同一 TAG 内要求唯一，前端以它为 key） |
| `providers[]` | **P12 专用**：提供者（`operator` / `condition` / `remark` / `prtsUrl`）；只有 `operator` 会用于取头像与星级 |
| `beneficiaries[]` | **P12 专用**：受益者名字，只渲染成纯文字 chips，**不取头像**（可以不在 `operators[]` 里，现状 272 处提及中有 26 个名字不在其中） |

## 3. 索引（页面打开时构建一次，之后全是查表）

| 索引 | 内容 | 说明 |
|---|---|---|
| `tagById` | `tagId → Tag` | — |
| `officialTags` / `playerTags` | 按 `source` 分组 | 保持 `tags[]` 顺序 |
| `officialByCategory` | 官方 TAG 按 `category` 分组 | 组序＝首次出现顺序 |
| `opEntriesByTag` | `tagId → 干员名 → 条目[]` | **跳过 `P12`**（组合条目没有 `operator`）；同一干员在同一 TAG 下的多条条目会聚合在一个数组里 |
| `opTagIds` | `干员名 → TAG id[]` | 未筛选时卡片上的 TAG chips、详情卡片的条目选择都用它 |
| `recSets` | `tagId → Set(荐名单)` | — |
| `recTagIdsByName` | `干员名/组合名 → 荐它的 TAG id[]` | 由 `recSets` 倒排，避免逐张卡片重复扫描 93 个 TAG |
| `subOptionsByTag` | `tagId → [{key, group, value}]` | 由该 TAG 全部成员的 `subTags` 去重而来；**`P12` 的子项＝组合名**（`key = combo|组合名`） |
| `p12Combos` | `P12.members` 中带 `combo` 的条目 | — |
| `providersCharId` / `providersRarity` | `干员名 → charId / rarity` | 由 `operators[]` 建，用于组合卡片的提供者头像 |

## 4. 筛选规则

### 4.1 多选 TAG ＝ 交集（AND）

干员必须出现在**每一个**已选 TAG 的成员里（对非 P12 的 TAG 判定）。官方设定 TAG 与玩家体感 TAG 同等参与，不做区分。

### 4.2 子 TAG ＝ 组内并集 + 组间仍是交集

选中某个 TAG 后，其下展开该 TAG 的 `subTags` 去重选项：

- 该 TAG 下勾选多个子项时取**并集**：成员的任一条目命中任一子项即可；
- 子项与 TAG 本身仍是 **AND**：先满足该 TAG 的成员资格，再看子项；
- 不勾任何子项 ＝ 该 TAG 不限子项。

命中判定看的是**条目级**的 `subTags`，因此"同一 TAG 内多条条目、末端子 TAG 不同"的情况会自然被覆盖（例如结城理在「闪避」下同时带 `物理闪避`、`法术闪避` 两条子 TAG）。

### 4.3 名称搜索

对**干员名**与**组合名**做子串匹配（不区分大小写），与 TAG 筛选同时生效（AND）。搜索不检索条件、备注、子 TAG 文本。

### 4.4 「阵容组合」（P12）只能单独选择

- 点选 P12 时：清空其它全部 TAG 选择与其子项；
- 已选 P12 时点选任何其它 TAG：取消 P12。

因此 P12 永远不与其它 TAG 共存，UI 上以**虚线描边 + 紫色文字 + 图标**标识，悬浮提示「仅可单独选择」。

### 4.5 结果区的划分

| 情形 | 干员区 | 组合区 |
|---|---|---|
| 未筛选 | 全部 398 名干员 | 不展示 |
| 只选了 P12 | **不展示**（避免"组合→全部干员"的空降噪音） | 14 张组合卡片 |
| 选了非 P12 的 TAG | 命中交集的干员 | 不展示 |

两区互不互斥：P12 不参与干员区的交集判定，干员区只看非 P12 的 TAG。

### 4.6 空结果

两区都为空时显示「没有同时满足全部所选条件的干员/组合。」

## 5. 荐的渲染

### 5.1 干员级「荐」

- **只认玩家体感 TAG**：未选任何玩家体感 TAG（含"只选了官方 TAG""未筛选"）时，一律不显示荐标识；
- **多选取交集**：同时选中多个玩家体感 TAG 时，干员必须出现在**每一个**已选玩家体感 TAG 的 `recommended` 名单里才显示；
- 官方 TAG 的 `recommended` 不参与（现状它们也没有该字段）。

标识为卡片右上角的**静态菱彩菱形**（旋转 45° 的方块，彩虹渐变，无动画），悬浮提示 = `荐：<TAG 名、…>（新手优先培养，仅供参考）`。

### 5.2 荐的排序

命中干员分两桶：先追加「荐」的干员，再追加其余干员；**两桶内部都保持 `operators[]` 的原顺序**（不使用 `recommended` 的数组顺序，该顺序按 `docs/output-standard.md` §6 不含展示优先级语义）。没有荐时就是 `operators[]` 原序。

### 5.3 阵容组合的「组荐」与「组员荐」

按 `docs/output-standard.md` §6「相互独立」的设定，前端**不复用干员级荐的判定**，而是直接看 P12 自己的 `recommended`：

| 概念 | 判定 | 展示位置 |
|---|---|---|
| 组荐 | 组合名 ∈ `P12.recommended` | 组合卡片右上角菱彩；组合详情卡片标题旁的菱彩 |
| 组员荐 | 提供者名 ∈ `P12.recommended` | 组合详情卡片中该提供者名字后的**小号菱彩图标**（无文字） |

两者都**不因多选其它玩家体感 TAG 而消失**（P12 本身也只能单独选择）。组荐与组员荐互不派生：给组合加荐不等于给它的提供者加荐。

### 5.4 文案

页面固定展示四块说明：使用说明 / 关于「荐」（定义与判定方式）/ 阵容组合的荐（含"带荐优先练、不带荐但已打算练则优先练组内带荐干员"两条）/ 免责说明（主观评定、可能不完整、不构成抽卡建议）。文案写死在页面里，**不来自 JSON**；若 `docs/output-standard.md` §6 的荐规则调整，需要同步改页面文案与 `src/utils/seo.js` 里的页面描述。

## 6. 卡片与详情卡片

### 6.1 干员卡片

头像（按 `rarity` 描边）→ 名字 → 星级 → `职业·分支` → 命中的 TAG chips。

- 有筛选时，chips ＝ 命中的那些 TAG 名；
- 未筛选时，chips ＝ 该干员出现过的 TAG 名取前 4 个，多余显示 `+N`；
- 有荐时右上角菱彩。

### 6.2 组合卡片

组合名 → 提供者头像行（最多 8 个）→ `提供者 N 名 · 受益者 M 名` → 机制摘要（`remark` 截断 96 字，带术语标注）。

### 6.3 干员详情卡片

点卡片打开：大头像、名字（有荐则带菱彩）、星级、`职业·分支 · 势力 · 实装日期`、PRTS 干员页外链；下方按 TAG 分组列出条目。

**条目范围的规则**：

| 情形 | 展示哪些 TAG 的条目 |
|---|---|
| 有筛选 | 该干员**命中的那些 TAG**（非 P12） |
| 未筛选 | 该干员出现过的**全部 TAG** |

若某 TAG 下勾选了子 TAG，该 TAG 的条目会先按子项过滤（过滤后为空则回退展示全部条目，避免空白）。每条条目展示 `条件` / `备注` / 子 TAG chips / 条目级 PRTS 外链。

### 6.4 组合详情卡片

组合名（有组荐则带菱彩）、`阵容组合 · 提供者 N 名`、条件、机制（`remark` 全文）、受益者 chips，然后逐个提供者列出：头像 + 名字（有组员荐则带小号菱彩）+ 条件 / 备注 / PRTS 外链。长内容在卡片内滚动，底部「关闭」按钮固定。

## 7. 备注/条件文本内的术语标注

- 术语表来自 `combat_glossary.json` 的全部 `sections[].terms[]`，按 `name` 长度**降序**拼成正则（保证「凋亡损伤·我方」先于「凋亡损伤」命中）；
- 匹配前先做 HTML 转义（`& < > "`），因此**备注里可以直接写尖括号原文**（如 `<塔纳托斯>`），前端会按字面展示而不会被当成标签吞掉；
- 命中的词包成 `<span data-combat-term="术语名">`，渲染为**天蓝色 + 灰色下划线 + 手型光标**；
- 点击（事件委托）弹出浮窗：标题＝术语名，内容＝`definition` ＋ `notes` 列表。

## 8. 前端对 JSON 的隐含约定（改数据前逐条核对）

| # | 约定 | 现状 | 破坏后的表现 |
|---|---|---|---|
| 1 | `operators[]` 覆盖全部成员条目中的干员名（含 P12 的全部 `providers`） | 是；**例外**：P12 的 `beneficiaries` 有 26 个名字不在其中 | 不在 `operators[]` 的干员**不会出现在干员区**；组合提供者会失去头像（按默认 6 星渲染） |
| 2 | 干员名唯一 | 是 | 索引按名字聚合，重名会被合并成同一张卡片、同一份条目 |
| 3 | `charId` 唯一且非空 | 是 | 卡片以 `charId` 为 key，重复会互相顶掉 |
| 4 | 组合名在 P12 内唯一 | 是 | 组合卡片与子项筛选都以组合名为 key |
| 5 | `P12` 这个 id 专用于阵容组合维度 | 是 | 该 id 有专门分支（互斥选择、组合区、组荐/组员荐） |
| 6 | `source` 取值 `official` / `player` | 是 | 分组与荐资格都依赖它 |
| 7 | 官方 TAG 无 `recommended` | 是 | 前端按空数组处理，官方 TAG 天然不产生荐 |
| 8 | `recommended` 元素必须是该 TAG 的成员名或组合名 | 由 `output-standard.md` §6 与 `recommend.py` 校验 | 悬空引用只会静默失效（不报错、不显示） |
| 9 | `rarity` 为 1–6 的整数 | 是 | 非法值按 6 处理 |
| 10 | 组合条目自身没有 `prtsUrl` | 是（14/14） | 前端不给组合条目渲染外链；若以后补上，需要同步加渲染 |
| 11 | `subTags` 的 `group` / `value` 是任意字符串 | 现状 7 个组名（闪避类型 / 子 TAG / 远程部署型召唤物与装置 / 救急路径 / 承载方式 / 增益类型 / 生效方式） | 前端只做 `{group,value}` 去重与精确匹配，不解释其含义，新增组名无需改动 |
| 12 | 同一 TAG 内同一干员可以有多条条目 | 是（现状 1 名干员存在多条） | 前端聚合为条目数组并列展示，不会被覆盖 |

## 9. 源项目改动时的自检清单

改完 `results/operator-tags.json` 后，按改动类型快速过一遍：

1. **新增/移动成员或提供者** → 确认该干员在 `operators[]`（约定 1）；确认 `condition` 写全硬性前提（详情卡片直接展示原文）。
2. **新增/改子 TAG** → 无需改前端，`subTags` 组名与取值是自由的（约定 11）；若子 TAG 用于 `P12`，注意前端把 P12 的子项当作**组合名**处理，不要给组合条目加 `subTags`。
3. **改荐名单** → 干员级荐要满足"多选取交集"的展示语义：只在部分 TAG 有荐的干员，在选择多个 TAG 时会不显示（这是设计预期，不是 bug）。P12 的荐元素只能是组合名或该组合的提供者名（约定 8）。
4. **新增 TAG** → 给一个稳定、唯一的 `id`；`source` 取 `official` / `player`；官方 TAG 目前不带 `recommended`（约定 7）。若新增的 TAG 需要"只能单独选择"这类特殊交互，需要在 `docs/ui-render-rules.md` 与前端页面同时登记。
5. **改 `operators[]` 字段** → 对照 §2.1 确认前端用到的字段仍然存在（`prtsUrl`、`faction`、`releaseDate` 只影响详情卡片的可选行）。
6. **改备注文本** → 尖括号可以直接写（§7）；文本里出现的术语会自动加蓝色下划线并可点击，若某个词不该被当成术语，应改 `combat_glossary.json` 的术语表而不是改备注。
7. **改数据结构（字段改名、层级调整）** → 前端不会降级兼容，会直接渲染异常或整页报错，必须同步修改 `src/pages/tools/better-combat-operator-filter.vue` 与本文。
