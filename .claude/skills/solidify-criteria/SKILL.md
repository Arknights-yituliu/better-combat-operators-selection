# Skill：评定标准固化（solidify-criteria）

## 适用与配套

- **适用**：开发者提出新 TAG／子 TAG 或修订评定标准，但只给「例子＋模糊词」；或对外释义（前端 tooltip 等）需要与评定标准同步。
- **配套**：`add-player-tag`（TAG 落盘全套步骤）、`update-version`（版本更新）、`add-new-operator`（新干员入 TAG）。
- **铁律**：不得凭模型记忆判断；不得自行放宽/收紧；评定标准未固化前不扫成员（除非开发者明确选择 stub 路线，见 `add-player-tag`）。

## 流程

### 1. 记录原话与例子

把开发者的原始定义、例子、语境**逐字**写进 `_out/评定标准固化-<TAG名>-记录.md`，不得转述走样。

### 2. 回源枚举样例

以定义中的机制关键词出发，回 `material_datas/PRTS/`、`material_datas/tag_pipeline/stats.json`、`deterministic.json`、`docs/abnormal-effects.md`、`docs/module-hidden-mechanics.md` 做全量搜索；沿参数轴扩展样例：

- 数值档（阈值上下、叠层/触发条件）、覆盖与持续时长、频率/间隔；
- 生效对象与方向（自身／友方／敌方）；
- 来源（技能／天赋／模组／召唤物／装置／模式限定模组）；
- 时点（部署时、技能开启时、受击时、常驻）；
- 触发前提（阻挡数、位置、目标类型、需队友配合等）；
- 与其它 TAG 的交叉（同一机制在别的 TAG 是否已有判据）。

每条样例输出：干员／机制、`文件:行号`、**按项目规则算出的数值**（面板取 `stats.json`；计算口径见 `docs/calc-rules.md`）、一句话归类理由。

样例集必须包含：开发者给的全部例子（正例）、阈值附近的**边界候选**、机制相近但不该收的**反例**（写清差在哪）。

### 3. 逐条裁定

- 用 AskUserQuestion 分批（每批 3–5 条；每条自带背景、数值、候选与选项；自创词当场解释，**不假设知识对齐**）。
- 回复模糊（「差不多」「看情况」）时继续追问，直到能落成「数值／条件／计数方式」。
- 留痕：问答逐字归档到 `_out/评定标准固化-<TAG名>-问答.md`。
  - **新 TAG／子 TAG 从零固化**：会话裁定 ＋ 归档 ＋ `docs/rulings.md` 登记。
  - **修订既有标准**（会动已发布产物）：先落《待裁定.md》自包含条文，回复后按四步折入。

### 4. 提炼可量化标准

- 从裁定反推：纳入／排除／门槛（数值与算式给全）／条件（精英化、技能、专精、模组与等级、模式限定、目标限制）／计数方式／与其它 TAG 的关系／约定。
- 文字遵守 CLAUDE.md「评定标准写作规则」：用「评定标准」一词、固定小标题、**无日期无轮次、不写编辑痕迹**。
- 边界与排除逐条进「边界与排除记录」，附证据 `文件:行号`。

### 5. 回归验证

把样例集当测试跑：开发者裁定的每个「纳入」例必须在标准下命中、「排除」例必须不命中（或已在排除记录中写明理由）。不一致先报告开发者再修，**禁止静默放宽阈值凑结果**。

### 6. 收尾

- 折入分文件 → `_merge_to_docs.py`；新 TAG 另按 `add-player-tag` 注册。
- `docs/player-tags-specify.md` 的定义句由开发者手改（不代写）。
- 同步对外释义（前端 tooltip 的通俗说明源文件；措辞不得使用项目专有词，出现术语当场解释）。
- 四步留痕 ＋ 跑校验套件（见 `handoff` skill §4）。

## 禁止

- 用模型记忆充当「语料」；用邻近窗口／印象抽取（一切回源、括号配对）。
- 未经裁定自行定阈值、自行排除。
- 把过程写进评定标准本身；标准文本不得能看出是哪一轮加的。
